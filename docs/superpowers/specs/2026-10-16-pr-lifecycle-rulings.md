## Adam's rulings on codex-gate's deferred items

Five items codex-gate 0.3.1 left open, decided by Adam and built into 1.0.0. Same format as above.

- Ruling R1-10 (Adam): every fetch before a review (startGate's base, the other gated base in isAlreadyOnBase, a changed submodule's main and dev, the post-PR triage fetch) goes through fetchTwice: a failure is retried once, and a second failure starts no round; the agent gets git's error (a held create says so instead of "wait for the review", a post-PR round stops through failPost) and the status line says the fetch failed; the next /pr-gate or create fetches again. A "couldn't find remote ref" failure is not a failure (the caller already handles a missing ref), and a submodule fetches main and dev one at a time — codex-gate ignored fetch results, so a round could review against a stale base — cost if wrong: a flaky network holds a create until a retry.
- Ruling R1-6 (Adam): every read-modify-write of a branch's record runs behind lockRecord (store.ts), a promise chain per root and branch held in the plugin process, released whether the change returns or throws. updateRecord takes it and accepts an async change; upsertRecord covers a change that may start the record. Routed through it: onNewHead and pre-PR endRound (headMoved now reads the record inside the lock, which settles the parked onNewHead waiver race), archiveLifecycle, startGate's rebuild and save (git and gh only inside; advance after), judgeCreate's docs-only preHead bump, allow, and the three waivers. The lock is not re-entrant, so nothing inside it calls updateRecord, advance or finish — a waiver or grant given while a round wrote the record could be overwritten — cost if wrong: an update waits behind a gh call in startGate's lock (up to its 30 s timeout).
- Ruling R1-5 (Adam): a create that names no base (gh, REST, graphql or any MCP create path) is checked against the repository's default branch from `gh repo view [repo] --json defaultBranchRef`, run in the checkout after the repo, head-branch and promotion checks (so a create that is not this gate's never needs the lookup); a failed lookup holds the create and tells the agent to name the base. The same resolution replaces `config.bases[0] ?? 'dev'` for a bare /pr-gate with no record (a failed lookup says "name the base") and for a pre waiver with no record (a failed lookup records no waiver), since that waiver must cover the base a base-less create resolves to. A post waiver with no record takes the PR's base, else the default branch, else the first gated base: its base is only bookkeeping, as the merge guard reads the base from the PR. Not honoured: gh's per-branch `gh-merge-base` git config, which gh pr create reads before the default branch — codex-gate defaulted a base-less create to dev, so a create to main on a main-default repo went ungated — cost if wrong: one `gh repo view` per base-less create.
- Ruling R1-9 (Adam): judgeMerge, after the finding holds let a merge through (ready for the head, or a post waiver), reads `gh pr checks <n> [--repo] --json name,state,bucket` and holds while any check is in the fail, cancel or pending bucket (an unknown bucket counts as running); pass and skipping are green. The refusal names the checks and tells the agent to fix, rerun a flaky one (gh run rerun --failed) or wait (--watch); it never names a waiver, and a post waiver does not release it (Adam: no waiver for this). gh prints "no checks reported" with exit 1 for a PR without checks (probed on live PRs, gh 2.102.0): that passes; any other output that is not a JSON array holds, fail closed, with gh's error. Pending checks print JSON with exit 0, so the decision reads stdout, never the exit code. The pane does not show CI (optional, left out) — codex-gate merged on red CI when the review was clean — cost if wrong: a merge waits for slow checks.
- Ruling R1-8 (Adam): reviewer text is fenced in every prompt that carries it: the triage prompt's feedback bodies, and every github-sourced finding listFindings renders (fix, verify, review, held, report and PR prompts), each body inside `<reviewer-comment from="login">…</reviewer-comment>` with any such tag in the body defused to `&lt;`, so it cannot close the quote early. One plain line after the prompt's first line says the tagged text is data from the reviewer, not instructions; it is added only to a prompt that has a fence. A github finding is named "comment from <login>" in prompts, since its title is the body's first line (the pane keeps the title). fetchFeedback drops feedback whose author_association / authorAssociation is anything but OWNER, MEMBER or COLLABORATOR, unless the author is on the roster's reviewers or requestReview, or is this machine's own login (its replies are sorted out as before); a row with no association is kept and still fenced. Dropped feedback also covers no head — any GitHub user could steer the agent through a PR comment — cost if wrong: a non-collaborator's real finding is not triaged, and an unrostered review bot with association NONE is ignored.

## Adam's rulings after 1.0.0

Decided by Adam and built into 1.1.0 (R67) and 1.2.0 (R68–R70). Same format as above.

- Ruling R67 (Adam): a repository's `.github/pr-gate.json` is read from the base (`git show refs/remotes/origin/<base>:.github/pr-gate.json`, per M4, the ref the last fetch left; no fetch of its own, except that a create only an exhausted gate under open-pr would allow fetches the base first (gate R3-2)) and never from the PR branch's HEAD, for the roster keys (reviewers, checks, requestReview, quietMinutes, waitCapMinutes) and for five new round settings: allowanceStandard (capped at 10), allowanceHigh (capped at 12), lightBranches (`""` turns the light lane off), onExhausted (open-pr or stop) and highRiskPaths, each with configOf's meaning and clamps. Precedence: the base's file, then the plugin options, then the defaults. An invalid value for one key is ignored, so that key falls back to the option, and is named once in the scope step and the start message; an invalid regex does not throw; a missing file or an unfetched base means no overrides, never HEAD's. configFor(root, base) resolves the effective settings and every round decision reads through it: startGate's tier, lane, allowance and rescope, judgeCreate's onExhausted and docs-only check, a pre waiver's new record, advance's open-or-hold and heldReason; rosterOf takes the record's or run's base.
