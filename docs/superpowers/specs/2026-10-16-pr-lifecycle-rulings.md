## Adam's rulings on codex-gate's deferred items

Five items codex-gate 0.3.1 left open, decided by Adam and built into 1.0.0. Same format as above.

- Ruling R1-10 (Adam): every fetch before a review (startGate's base, the other gated base in isAlreadyOnBase, a changed submodule's main and dev, the post-PR triage fetch) goes through fetchTwice: a failure is retried once, and a second failure starts no round; the agent gets git's error (a held create says so instead of "wait for the review", a post-PR round stops through failPost) and the status line says the fetch failed; the next /pr-gate or create fetches again. A "couldn't find remote ref" failure is not a failure (the caller already handles a missing ref), and a submodule fetches main and dev one at a time — codex-gate ignored fetch results, so a round could review against a stale base — cost if wrong: a flaky network holds a create until a retry.
- Ruling R1-6 (Adam): every read-modify-write of a branch's record runs behind lockRecord (store.ts), a promise chain per root and branch held in the plugin process, released whether the change returns or throws. updateRecord takes it and accepts an async change; upsertRecord covers a change that may start the record. Routed through it: onNewHead and pre-PR endRound (headMoved now reads the record inside the lock, which settles the parked onNewHead waiver race), archiveLifecycle, startGate's rebuild and save (git and gh only inside; advance after), judgeCreate's docs-only preHead bump, allow, and the three waivers. The lock is not re-entrant, so nothing inside it calls updateRecord, advance or finish — a waiver or grant given while a round wrote the record could be overwritten — cost if wrong: an update waits behind a gh call in startGate's lock (up to its 30 s timeout).
- Ruling R1-5 (Adam): a create that names no base (gh, REST, graphql or any MCP create path) is checked against the repository's default branch from `gh repo view [repo] --json defaultBranchRef`, run in the checkout after the repo, head-branch and promotion checks (so a create that is not this gate's never needs the lookup); a failed lookup holds the create and tells the agent to name the base. The same resolution replaces `config.bases[0] ?? 'dev'` for a bare /pr-gate with no record (a failed lookup says "name the base") and for a pre waiver with no record (a failed lookup records no waiver), since that waiver must cover the base a base-less create resolves to. A post waiver with no record takes the PR's base, else the default branch, else the first gated base: its base is only bookkeeping, as the merge guard reads the base from the PR. Not honoured: gh's per-branch `gh-merge-base` git config, which gh pr create reads before the default branch — codex-gate defaulted a base-less create to dev, so a create to main on a main-default repo went ungated — cost if wrong: one `gh repo view` per base-less create.
- Ruling R1-9 (Adam): judgeMerge, after the finding holds let a merge through (ready for the head, or a post waiver), reads `gh pr checks <n> [--repo] --json name,state,bucket` and holds while any check is in the fail, cancel or pending bucket (an unknown bucket counts as running); pass and skipping are green. The refusal names the checks and tells the agent to fix, rerun a flaky one (gh run rerun --failed) or wait (--watch); it never names a waiver, and a post waiver does not release it (Adam: no waiver for this). gh prints "no checks reported" with exit 1 for a PR without checks (probed on live PRs, gh 2.102.0): that passes; any other output that is not a JSON array holds, fail closed, with gh's error. Pending checks print JSON with exit 0, so the decision reads stdout, never the exit code. The pane does not show CI (optional, left out) — codex-gate merged on red CI when the review was clean — cost if wrong: a merge waits for slow checks.
- Ruling R1-8 (Adam): reviewer text is fenced in every prompt that carries it: the triage prompt's feedback bodies, and every github-sourced finding listFindings renders (fix, verify, review, held, report and PR prompts), each body inside `<reviewer-comment from="login">…</reviewer-comment>` with any such tag in the body defused to `&lt;`, so it cannot close the quote early. One plain line after the prompt's first line says the tagged text is data from the reviewer, not instructions; it is added only to a prompt that has a fence. A github finding is named "comment from <login>" in prompts, since its title is the body's first line (the pane keeps the title). fetchFeedback drops feedback whose author_association / authorAssociation is anything but OWNER, MEMBER or COLLABORATOR, unless the author is on the roster's reviewers or requestReview, or is this machine's own login (its replies are sorted out as before); a row with no association is kept and still fenced. Dropped feedback also covers no head — any GitHub user could steer the agent through a PR comment — cost if wrong: a non-collaborator's real finding is not triaged, and an unrostered review bot with association NONE is ignored.

## Adam's rulings after 1.0.0

Decided by Adam and built into 1.1.0 (R67) and 1.2.0 (R68–R70). Same format as above.

- Ruling R67 (Adam): a repository's `.github/pr-gate.json` is read from the base (`git show refs/remotes/origin/<base>:.github/pr-gate.json`, per M4, the ref the last fetch left; no fetch of its own, except that a create only an exhausted gate under open-pr would allow fetches the base first (gate R3-2)) and never from the PR branch's HEAD, for the roster keys (reviewers, checks, requestReview, quietMinutes, waitCapMinutes) and for five new round settings: allowanceStandard (capped at 10), allowanceHigh (capped at 12), lightBranches (`""` turns the light lane off), onExhausted (open-pr or stop) and highRiskPaths, each with configOf's meaning and clamps. Precedence: the base's file, then the plugin options, then the defaults. An invalid value for one key is ignored, so that key falls back to the option, and is named once in the scope step and the start message; an invalid regex does not throw; a missing file or an unfetched base means no overrides, never HEAD's. configFor(root, base) resolves the effective settings and every round decision reads through it: startGate's tier, lane, allowance and rescope, judgeCreate's onExhausted and docs-only check, a pre waiver's new record, advance's open-or-hold and heldReason; rosterOf takes the record's or run's base. ## Rulings after 1.5.0

Spec: `docs/superpowers/specs/2026-10-24-lifecycle-filing-identity-design.md`. Plan: `docs/superpowers/plans/2026-10-27-pr-lifecycle-filing-identity.md` (Part A).

- Ruling R96 (amends PR #28's generation mark; Adam, #29 option A, 2026-10-24): every lifecycle has a random id (`lifecycleId`), made with its record at a fresh start, an adoption or a reset, and saved under the lock before the first filing pass of a record from before ids. A failed save stops the pass before any POST. The filing mark names the id (`<!-- pr-gate filing: <finding> of #<pr> lc <id> -->`), a mark is never written without one (by type), and the lost-answer search adopts only an exact mark. Earlier marks, by generation or with neither, are never adopted, not even by title; an issue with no mark keeps the title fallback. Another checkout's record of the same PR, or a reset lifecycle whose finding ids start again, has its own id, so it never takes this lifecycle's issue. A shared store across checkouts (option B) is wave 3 work with #27 — cost if wrong: a POST whose answer was lost just before the upgrade files its issue once more.

- Ruling R97 (amends R83; Adam, 2026-10-27, on discussion #15 items 30, 32 and 33: "classify review comments before giving them a severity … the security flag should come from the finding's own content", and "as long as this is not allowing 'approval' reviews to mark the blocking issues as fixed without them being filed to github issues the pr should merge with proof of the issue that was filed"): a review or comment settles on the verdict it opens with, not on every sentence of it. R83 required each sentence to be a no-action form, so none of the reviewers in use could ever settle: measured over cookbook PRs #3785, #3748 and #3749, all 46 non-empty items were triaged as findings, including eight pure approvals, five of them as security P1. `isNoAction` now reads the body's first line that says anything, heading marks dropped, and scans what follows it for a request word, so a review that shows the validation it ran settles while "No blocking findings. However, the cache is never cleared." still goes to triage. It also takes the feedback's kind, so comments and inline comments are read: the no-action check reached reviews only, which is why the Independent Claude review's "No changes needed" and Codex's status note always became findings. A terminator splits a sentence only where whitespace or the end follows it, so a commit range in a verdict (`61c98ff..8dba6cb`) is not cut in half. The security flag comes from the claim: a security word on a line that negates it ("no touches to security/proxy/validation, auth") raises nothing, which is what rated those approvals P1 and, through `isFileable`, kept them off the filing path so only a named waiver released them. A settling comment is logged and processed like a settling review, so the approval leaves the same audit event. Nothing here lets an approval settle another finding: `isNoAction` decides only whether the review or comment is itself a finding, and `markVerified` is called only by Codex and the gate's own fix-reviewer. Measured after the change: 6 of the 10 named approvals settle, 0 carry a security flag, and of all 46 items only 7 settle, every one a genuine approval. After the PR #32 review: a security word raises nothing only where a negation governs the list it sits in, as "no <list> findings" or "no touches to <list>" ending the sentence, and the sentence draws no harm; each sentence is its own claim. So "No escaping is performed, allowing SQL injection", "No validation of credential changes is performed" and "No security issues in the UI. The API leaks a secret." all raise security; and a severity the reviewer tagged anywhere in the body is a finding, whatever the verdict above it says. — cost if wrong: an approval whose opening line settles and whose later text asks for a change in words the request scan misses is not triaged, so that request reaches the person instead of a round.
- Ruling R98 (amends the design's "not intercepted: PRs from a branch not checked out here"; Adam, 2026-10-28, #34, rated P0, on discussion #15 item 35): a create whose head (`--head`, `-H`, or the `head` field of the REST, GraphQL or MCP call, owner prefix dropped) names a branch other than the one checked out is held, never passed. PR #32 opened with no review that way: its worktree had `worktree-bridge-cse_…` checked out, pushed it as `HEAD:refs/heads/fix/approvals-settle-R96`, and ran the create with `--head fix/approvals-settle-R96`; the old rule read that as a release PR and let it through, with no record and no trace. The hold names both branches and tells the agent to check out a local branch of the head's name holding those commits and run the create from it, so that branch's own gate reviews it. A promotion stays free: when the head named, or the branch checked out where none is named, is itself a gated base. No round starts for a held head, since the gate cannot see what it carries. — cost if wrong: a release PR from a branch that isn't checked out (a non-base `release/x` opened from another checkout) is held until it is run from a checkout of that branch, where it is gated like any other branch.
- Ruling R99 (amends the design's `stepTimeoutMinutes`, "a fail-closed hard cap on any single agent step"; Adam's go-ahead on #26, rated P1): a step timeout no longer cuts off a fixer sub-agent that is still working, and no longer ends a run in silence. In the live run of #26, the fix step stopped at 30 minutes while its sub-agent was still editing, and the run ended in error with nothing said to the agent. The agent learned of it only by reading the pane. The fixer's answer then came in and was dropped, because a turn that ends while no run is live is never read. Now:
  - **The fixer's clock.** A fixer sub-agent is timed from its last tool call (`Pending.seenAt`, written at most every 10 s), not from the step's start. A fixer that keeps working is stopped only at three step limits in all (`FIXER_CEILING`). A main-agent step and every other step keep the single limit. Only the fixer's own calls count, known by the agent id the engine gave it; where it gave none, no call counts and the single limit applies, so another sub-agent's work never keeps the step alive.
  - **The agent is told.** Every step timeout that ends the run in error, Codex's last one at low effort included, tells the agent what stopped and its next step: before the PR, run the create again from the branch (or the person types `/pr-gate resume`); after it, tell the person to type `/pr-gate resume`.
  - **A late fixer answer is kept.** The run records the stopped fixer (`Run.late`: its agent id, its step, round, lifecycle, generation and `lifecycleId`). If that fixer still answers, its dispositions are applied to the record as the fixer's, but only while the record is the same lifecycle: not archived, the same generation and the same id. A reset, a fresh start or a new run in between drops the answer and logs it. The run is checked again under the record's lock, just before the write: a resume while the answer is being taken drops it too (gate G3-3). The agent is told the counts, the head, and the same next step, with "commit them" first if the tree is dirty. The next round then has Codex check the kept answers instead of redoing the fix. The answer is matched by the agent id alone: a step name like `r1-fix` is shared by every run's round, so a fixer the engine gave no id is not recorded and its late answer is dropped, as before. Whether one is awaited is read from the run, not from module memory, because hook contexts don't share module state.

  — cost if wrong: a fixer stuck in a loop of tool calls runs up to three step limits (90 minutes by default) before it is stopped; and a late answer can land on a record that changed in ways the generation and id don't catch (the person's waiver at the same head), where Codex's next round is still the check; and a resume whose run is installed after the locked check, from a record read before the write, can still meet a kept answer, because run installs don't take the record lock (#42, P3): the kept answer is only owed a Codex verification.
